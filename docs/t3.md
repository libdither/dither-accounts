# T3 Code (kind `t3`)

[T3 Code](https://github.com/pingdotgg/t3code)'s coding threads as chats, on the `chat` interface ([chat.md](chat.md)):
each thread is a conversation with its agent, its project a space, and a message sent there is the thread's next
turn. dither-chat's hub shows them under the network `t3`, so threads started elsewhere (by [bugwatch](bugwatch.md), by
another agent, by you in T3 Code) can be read and answered from the inbox.

```
 T3 Code on this machine
   ├─ the shell stream (/ws, orchestration.subscribeShell) ──▶ thread summaries as they change ─┐
   ├─ the MCP endpoint (/mcp: t3_project_list, t3_thread_read) ◀── reads a changed thread ──────┤ extractors/t3 ─▶ chat facts
   └─ the t3 command (auth session issue, thread send) ◀── sessions; a message from the hub ────┘
```

Code: `extractors/t3/src` (`t3.ts` reaches T3, `map.ts` maps, `account.ts` keeps the threads and decides what to
read and emit, `main.ts` is the extractor), its fake T3 in `extractors/t3/test`.

## Adding it

On the manager's page **Add → T3 Code**, or in dither-chat's Add an account → T3 Code. It needs T3 Code running on
the same machine as the manager, as the same user. The form's fields are all optional:

- **Projects**: which projects to show, as titles (any case), project ids or folders (a project whose folder is or is
  under one), separated by commas. Empty: every project.
- **The t3 command**: its absolute path, when `t3` is not on the manager's PATH. Without one it also looks in the
  per-user Nix profile (`/etc/profiles/per-user/$USER/bin`); `T3_BIN` in the environment overrides both.
- **T3 Code's data directory**: only when T3 keeps its data elsewhere than `~/.t3` (`T3CODE_HOME`).

There is no sign-in: it makes its own T3 sessions with the command line (below).

## How it reaches T3

- **The server's address** is in `<data dir>/userdata/server-runtime.json`, which a running T3 Code writes. Without it
  the account is offline (layer `T3 Code`) and tries again, waiting up to a minute between tries.
- **Two sessions**, made with `t3 auth session issue`, both with the scope `orchestration:read` only, so neither can
  change a thread. One has the subject `mcp-client`, for the MCP endpoint, which takes no other. The other is a plain
  bearer session for the shell stream, which takes no MCP client's. Each lasts 7 days and is kept in the account's
  `secret.json`. It is replaced (and the old one revoked) a day before it ends, or when T3 refuses it.
  In `t3 auth session list` they are labelled `dither-accounts <account label> (reads)` and `(live updates)`.
  Removing the account leaves them until they end: revoke them there if you want them gone sooner.
- **Live updates** come from `orchestration.subscribeShell` on `/ws`, the feed T3's own sidebar draws from: Effect RPC
  frames in JSON, a one-use ticket from `POST /api/auth/websocket-ticket`, and `orchestrationProtocol=2` in the
  address. A snapshot of the active threads comes first, then each thread's summary as it changes (status, item count,
  pending request, last visit). A dropped stream connects again; its fresh snapshot brings what changed meanwhile.
  If T3 answers 426 (another orchestration protocol than this code speaks), the extractor reads `t3_thread_list`
  every 15 s instead (layer `live updates` says so). That list is the 100 threads changed last, and each read costs
  T3 a scan of every thread.
- **Reading a thread** is `t3_thread_read` on the `messages` view, from the last turn read on. A thread is read only
  when its summary changed, and at most once every 2 s. A text longer than one read's 50,000 characters is read on
  by `textOffset`.
- **Sending** runs `t3 thread send --json <thread> -` with the message on stdin. The CLI signs in for that one call
  at the owner's own access and signs out, and the turn is queued behind a busy run: nothing is interrupted. A
  lasting session could not send there: T3 caps a session's sends at the runtime mode it was given, and refuses a
  thread above it.

## What shows

| T3 | chat |
|---|---|
| a project | a space (`project:<id>`, kind community), named by its title |
| a thread | a channel in its project's space, named by its title. Its topic is the state and the model: *Working*, *Waiting for your answer*, *Finished*, *Failed*, *Stopped*, *Idle* (`· model`). An archived thread is archived |
| your prompt | your message. That includes one sent from dither-chat: T3 marks those as a client's, so the account keeps their ids in `sent.json` |
| a prompt another agent wrote (a parent thread, bugwatch or a script through T3's MCP) | a message from *Another agent* |
| the agent's reply | a message from the agent (*Claude*, *Codex*, …), its markdown as it is. A run with several replies is several messages |
| tool calls, commands, file changes, reasoning | left out |
| a run waiting on a question or an approval | a message from the agent, *Waiting for your answer to its question. Answer it in T3 Code: <link>*, once per request; it makes the chat unread |
| a run that failed | a message from the agent, *The run failed: <error>* |
| opened in T3 Code after its latest turn | read here too (a `read` event) |

- **Which threads:** the ones T3's sidebar shows, from its shell snapshot: active and recently settled threads.
  Older settled ones show again once they change. Subagents spawned inside another thread are left out; forks and
  delegated threads are shown.
- **History:** a thread seen at start shows its latest 20 turns; older ones come as dither-chat pages back
  (`history`). A thread that appears later shows its latest 20 turns too, as new messages.
- **Long replies:** kept whole up to 200,000 characters, then clipped with a note.
- **A turn still being written** waits until it is done, and so do the turns after it, while the run goes on. Once
  the thread stopped, what is there shows as it is.
- **Marking read** in dither-chat stays there: it never changes the thread in T3. Typing does nothing.

Not built:
- **Starting a new thread** from dither-chat. The chat interface has no way to start a conversation in a space with a
  first message; start it in T3 Code, or with `t3 thread start`, and it shows up here.
- **Answering a question or an approval.** A message is queued as the next turn, so it does not answer what the run
  waits on; the note links to the thread in T3 Code.
- **Files, edits, reactions.**

The extractor logs thread ids, counts and states, never what a thread says.

## Status

Layers, outermost first: `t3 command` (found), `T3 Code` (running), `sessions` (read-only), `live updates` (the shell
stream, or the list every 15 s and why), `threads` (how many, in how many projects). The account is offline while T3
is not running, and needs you only when there is no `t3` command (attention: give its path). `action resync` reads
everything again.

Environment, for tests: `DITHER_T3_POLL_MS` (15000), `DITHER_T3_RETRY_MS` (5000, doubling to a minute),
`DITHER_T3_READ_GAP_MS` (2000).

## Testing

`extractors/t3/test/map.test.ts` tests the mapping. `test/t3.test.ts` runs a manager with the kind on a fake T3
(`extractors/t3/test/fake-t3-server.ts`, its CLI `fake-t3.ts`) and an app with the hub's chat grant. It covers:

- projects, threads and turns, with tools and subagents left out;
- a reply longer than one read, kept whole;
- turns arriving live, a request waiting, a read in T3;
- a send through the CLI and the agent's answer, paging back;
- a revoked session replaced, a dropped stream reconnected;
- the list instead of the stream.

What only a real T3 Code checks: the shell stream's frames and the MCP endpoint's answers as the server sends them
today, and that `t3 thread send` reaches the thread. Check with a thread of your own, in a scratch project.
